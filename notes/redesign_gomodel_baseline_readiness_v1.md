Already acquired original source establishes why a source-aware comparator cannot simply check required-field labels. GuardrailEditor disables identity/type in edit mode and delegates configuration inputs to SchemaFields. In the textarea branch, SchemaFields renders a required marker in the label but does not set the textarea's required attribute. GuardrailsStore.submitForm checks name, type and timeout, then calls buildGuardrailPayload and the original mutation wrapper. guardrailEditForm merges configuration defaults, normalizes other fields and preserves a stored known type. buildGuardrailPayload omits empty description, user_path, failure mode and timeout through undefined values before JSON serialization. These are source observations, not claims about altered-record outcomes.

A competent D comparator must preserve those original load/default/field conversion, native constraint validation, submit guards and serialization behaviors. It must record its information budget and predicted request payload, not just accept/reject. Reimplementing required markers as stronger constraints would create an artificially weak comparator. Original frontend execution with a non-mutating interception boundary is a possible implementation; its agreement with ordinary native requests must be qualified before using it. It would predict client preflight behavior, not prove server acceptance or full persistence-frame preservation. The comparator recipe, coverage and decision rule remain unresolved and no superiority claim is justified.
