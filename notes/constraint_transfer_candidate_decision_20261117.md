# Constraint-transfer candidate: specification and evidence limits

The preceding turn completed scorer engineering. This turn makes the proposed treatment and its failure criteria concrete in protocol/constraint-transfer-candidate-v1.md. It preserves the original workflow-compatibility objective and treats automatic acquisition as an unproven possible contribution.

The treatment transfers explicit frontend predicates only with supported operation/actor/lifecycle scope, field mapping, transformation and observation point. Its distinguishing hypothesis concerns avoiding incorrect global invariants. A naive transfer ablation alone is inadequate: the design requires a source-aware practical comparator with identical evidence and setup accounting. Accuracy gains caused solely by more unknown results do not establish benefit. No new source parser, complete adapter or scientific measurement is claimed.

Revisited the previously cited primary paper Managing data constraints in database-backed web applications (https://hyperloop-rails.github.io/278.pdf), especially its study overview and validity limitations. It already studies constraint consistency, evolution and checking in Rails applications; a new claim cannot rest on the existence of cross-stack mismatches. Its stated omission of frontend JavaScript from that implementation is not proof that JavaScript constraint analysis is novel: ViewPoints and the earlier literature checks remain relevant. This is a scoped source review, not a new independent claim-verification pass.

The paper's project landing page (https://hyperloop-rails.github.io/vibranium/) links a GitHub account, whose displayed checker fork points to https://github.com/manageconstraints/data-constraint-checker. Only landing/repository README and directory listings were viewed. README describes Ruby-based extraction across twelve applications and version history; it does not establish a ready-to-run, independently labelled API/native-workflow benchmark. Neither application lists/pins, source logs, tests nor labels were opened. No cloning, dependency installation or execution followed. This lead is not admitted as a dataset, and no guarantee of held-out status is inferred from not opening its labels.

The unresolved gates are explicit: automatic source acquisition/mapping, a qualified information-matched comparator, independent workflow/constraint sampling and label evidence, and a feasible cost/effect design. The method specification can now be challenged before additional experiments. It cannot support a Q1 claim on its own. No paid compute, new application observations or finding-driven replacements occurred.
