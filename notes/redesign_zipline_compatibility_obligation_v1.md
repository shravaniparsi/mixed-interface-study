# Zipline URL compatibility obligation: source basis v1

This is a development source interpretation, not a runtime result or defect finding. At original revision 49b81a290dfa59906c4d2a69f729460fc6357134, the native creator calls POST /api/user/urls, whose description says it creates a shortened URL for the authenticated user. The native grid reads GET /api/user/urls and passes those returned records directly to EditUrlModal. That editor PATCHes /api/user/urls/:id. Both original list and update handlers restrict records by the authenticated user's ID. No separate API-origin record kind or editor exclusion is present in these inspected routes/components.

Evidence: wave-11 files 55 and 57 (individual and collection routes); wave-14 files 4, 7 and 8 (editor, native creator and grid); wave-12 file 15 (API-token/browser-session user middleware). Their acquired blob identities and SHA-256 values are retained in the respective frozen collection records. These connected original call paths support a compatibility obligation for ordinary URL records owned by the same user to be offered to this editor. They do not establish that every unusual accepted representation is contractually invalid, or that frontend normalization constitutes a bug.

An ordinary native/API control can demonstrate feasibility for its exact values and principal. It cannot establish a universal obligation for conditional embed configurations, write-only passwords, administrative imports, unsupported lifecycle states or all API clients. Later observations must retain those distinctions and any unresolved defect attribution.
