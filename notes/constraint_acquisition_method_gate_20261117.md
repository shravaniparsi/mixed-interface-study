# Constraint acquisition: verified prior art and next design gate

This review assesses the proposed shift from executing hand-written checks to acquiring constraints. It does not register another experimental cohort, reopen closed runs, or establish novelty. ViewPoints was already present in the project's initial literature set; this review must not describe it as a newly discovered omission. AutoBypass and the version-specific RBCTest comparison sharpen the present design decision.

## Proposed question and decision

Candidate empirical question: when does frontend evidence improve acquired API-test oracles after accounting for legitimate differences between interfaces? This is a narrower, measurable question; it is not a validated new method or a claim that frontend-derived testing is new. Possible value would be evidence about constraint transfer and acquisition cost, rather than repeating that direct requests bypass client validation.

A credible comparison must separate information access from method quality. Compare an OAS-only baseline with a documented frontend-evidence extension, and separately compare methods receiving the same complete evidence. The former measures added information; it cannot establish algorithm superiority. Native RBCTest, a modified RBCTest adapter, direct frontend-rule extraction and an independent task-contract reference must retain distinct labels. Do not deny existing logical-oracle capabilities by using status-code-only checks as the strongest baseline.

The evaluation unit should be a project/workflow constraint with an applicability condition, not each generated payload or repeated execution. Score recovered predicates against independently authored requirements/tests where they actually establish intended behavior, retaining unresolved labels. Record mapping failures, unsupported predicates, unknown verdicts, false alerts and missed violations separately. Count source-to-API mapping work, annotation/review time, calls/tokens and execution setup; elapsed assistant time is not measured human labor savings. Preserve normal inputs and legitimate cross-interface differences alongside violations.

The null-state calibration is exposed development material only. Its nonnull checks were supplied with issue knowledge, so its zero incremental exception detections answer neither automatic inference accuracy nor cost savings. It does show why giving issue-derived rules only to one method would be unfair. Likewise, an array predicate disagreeing with a tolerant constructor is not automatically a false positive against an API contract.

Before new collection or paid execution, four gates remain: an explicit method/adapter and falsifiable benefit; an independent sampling frame chosen without observed failures; independently recoverable correctness labels with an exposure split; and bounded all-in cost including a competent baseline. None is satisfied merely by downloading another benchmark. Existing closed schedules remain closed. No automatic corpus expansion or next runtime is authorized by this literature note.
