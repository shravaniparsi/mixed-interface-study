## Viseron

The original AddUserDialog submits name, username, password and role. Its edit UserDialog keeps name/username/role/camera selections, passes preferences to the hook, and disables Save only while the mutation is pending. The actual authUpdateUser network serializer destructures only id/name/username/role/assigned_cameras, PUTs the four body properties to /auth/user/{id}, and converts empty/absent camera selections to null. Preferences and enabled are not in that original emitted body. Backend User.as_dict supplies id/name/username/role/enabled/assigned_cameras/preferences; GET /auth/user/{id} looks up the immutable ID, despite a frontend helper's parameter being named username. Do not confuse the variable name with the backend identifier contract.

scripts/extension/materialize_viseron_user_update_v1.mjs preserves that complete source-derived request. It supports original UUID-hex identities, string name/username, the three original roles and complete readback; nonstandard representations are unavailable rather than guessed. It does not trim/casefold the request because the original frontend does not. Backend update_user strips name and strips/casefolds username, which must be retained as observable normalization rather than an incompatibility claim. Native request qualification is still required.

The original route schemas are Voluptuous objects with required string properties and role membership checks. Evaluate the original executable validator/version as a competent schema baseline; do not replace it with invented frontend rules or silently call it JSON Schema. Final S implementation/dialect support remains pending. No validator has been run on scientific inputs.
