INDEPENDENT VERIFICATION OF THREE NOVELTY SOURCE CLAIMS
Checked 6 November 2026 by a separate skeptical verifier. Input: novelty_search.txt. No benchmark was executed and no plan or manuscript was edited.

1. RESTLER ACTIVE PROPERTY CHECKERS — CONFIRMED WITH SCOPE LIMITS

Claim: Active API follow-up tests and persistent-state/property checks predate our proposed method.
Primary source: Atlidakis, Godefroid and Polishchuk, Checking Security Properties of Cloud Service REST APIs, ICST 2020 Industry Track, DOI 10.1109/ICST46399.2020.00046.
Paper: https://patricegodefroid.github.io/public_psfiles/icst2020.pdf
Official metadata: https://conf.researchr.org/details/icst-2020/icst-2020-Industry/1/Checking-Security-Properties-of-Cloud-Service-REST-APIs
Read: introduction, Sections III-A and III-B, Figures 1–4, efficiency discussion.
Exact supporting excerpt, introduction: “generates new API requests to test specific rule violations”.
Confirmed: four checkers cover use-after-free, resource leaks, resource hierarchy and user namespaces. The leak checker probes state after failed creation. The algorithms select subsequent requests using produced/consumed object types and prune redundant checks.
Constraint: the inspected checkers operate on API requests. They do not establish equivalence between a native UI action and an API route. Dependency-derived follow-up requests alone are therefore also established, not merely hand-written suffix checks.
Rejected extension: describing generic continuation testing or consumer-based follow-up selection as new.

2. CONSTRUCTED HTTP SEMANTIC SEQUENCES — CONFIRMED AS A PREPRINT METHOD

Primary source: Omur Sahin and Andrea Arcuri, Validating HTTP Semantics in REST APIs With Constructed Call Sequence Scenarios, arXiv:2608.16239v1, 17 August 2026.
Text: https://arxiv.org/html/2608.16239v1
Version record: https://arxiv.org/abs/2608.16239
Read: abstract, Sections 3.2, 4.1–4.3 and Table 2.
Exact supporting excerpt, abstract: “a new phase is executed”.
Confirmed: the EvoMaster extension constructs additional HTTP sequences from existing tests for nine semantic oracles. Section 3.2 compares GET observations around failed PUT/PATCH operations, handling status-specific credentials, resource binding and response nondeterminism. The evaluation includes 36 WFD APIs and quartz-manager.
Constraints: verified as an August 2026 preprint, not a verified journal publication. HTTP-rule interpretations belong to these authors; this check did not independently validate every RFC interpretation. The side-effect-after-failed-modification oracle was implemented but found no such natural faults in the reported WFD experiment. Neither its inclusion nor Quartz's inclusion establishes a detected Quartz defect. The inspected method does not validate native UI/API substitution.
Rejected extensions: all nine oracle classes found natural defects; all included applications had detected defects.

RESOLUTION SUMMARY

Three proposed core source pairings confirmed within the stated scopes. Four broader extensions rejected: novelty of generic follow-up testing, all nine semantic classes yielding natural faults, every included API yielding a defect, and turnkey PetClinic reproductions. No core source rejected for nonexistence or metadata. Experimental applicability remains untested. APIDocX and LoBREST were outside this verification assignment and must not be relabelled independently confirmed from this log.

Design implication: isolate native UI/API workflow preservation from established API semantic checks and dependency-derived follow-up requests. Use the historical PetClinic records only after explicit eligibility and reproduction checks. These verified sources narrow the candidate contribution; they do not establish exhaustive prior-art coverage or disprove every possible mixed-interface contribution.
