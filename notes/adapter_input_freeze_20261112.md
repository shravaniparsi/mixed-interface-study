# Adapter feasibility: source-input freeze

Selection commit c1a7026e fixes three capability-selected converter releases. Input commit 930b3eb9 fixes the source API contract and complete 48-case inventory before inspection of pinned converter implementation bodies or our own converter outcomes. Commit ce53d8b6 adds semantic controls. The public prior-art and issue exposure disclosures remain applicable; this is not a claim of wholly blind research.

The two write operations deliberately have different semantics: creation applies server defaults only to absent top-level fields, while partial update preserves omitted members and uses the declared recursive removal/replacement rules. Explicit null is therefore not interchangeable with omission, and its meaning differs between operations. Both schema and operation descriptions state this distinction. The update schema contains no defaults. The fixture accepts two declared media types for its update algorithm; this is not a claim that RFC 7396 standardizes application/json as its media type.

There are 24 fixed input shapes per operation, including scalar values, explicit null, false, zero, empty values, ordered arrays, nested objects, nested removal and ordinary complete controls. The scope is a controlled synthetic source API. It cannot establish real-workflow incidence, novel natural defects, or superiority of a new semantic-inference method. The source expectations are handwritten and visible to every comparator.

Independent validation using openapi-spec-validator 0.7.2, openapi-schema-validator 0.6.3 and jsonschema 4.26.0 accepts the OpenAPI document, all 48 source inputs and 120 expected-state objects. Twelve deliberately invalid validator controls are rejected. This validates source schema conformance, not converter compatibility or business-state correctness. The three semantic-control tests separately check the declared nested update and creation rules. Fully pinned validation dependencies and a reconstructable receipt are retained.

The original inventory's pending-validation flag is a historical freeze-time statement; manifests/openapi-adapter-input-validation-v1.json supplies the later validation result. No frozen inputs were changed to obtain acceptance. No converter has been installed, inspected at its pinned implementation or executed in this phase.

Before scientific execution, the remaining requirements are an independently observable reference backend, public-contract-based tool bindings, ordinary-case qualification, frozen per-subject runners/dependencies, full raw request and state capture, complete baseline decisions, and a fixed repeat/cost schedule within the previously stated envelope. Unsupported bindings or operations must remain in the feasibility denominator. Do not add or remove cases after viewing generated tool schemas or execution outcomes.
