# Post hoc README readback investigation

The closed scientific results are unchanged. An offline audit found five records with an immediate empty final branch list and main in the subsequent read-only failure snapshot: repetition 1's starting native/native control; repetition 2's ordinary API/API, initialize=false API/API, initialize=false native/native, and ASCII-description API/API cases. Each first queried the same branch-list endpoint while the repository was empty. This cross-path pattern is inconsistent with treating these records as a native-continuation-only failure after API production.

Official GitLab source pinned at 358d690d91c78748a130cb46358c12eaa22275aa provides a plausible mechanism. In lib/api/branches.rb, the branch-list route wraps response generation in cache_action, using the project, user and declared parameters as key inputs and a 30-second expiry. The helper in lib/api/helpers/caching.rb uses cache.fetch to store the serialized response and pagination headers. This is response caching, not just serialization caching of individual existing branch objects. The separate single-branch route is not wrapped in this action cache at that location; that does not prove it is uncached throughout its call chain.

Sources: https://github.com/gitlabhq/gitlabhq/blob/358d690d91c78748a130cb46358c12eaa22275aa/lib/api/branches.rb and https://github.com/gitlabhq/gitlabhq/blob/358d690d91c78748a130cb46358c12eaa22275aa/lib/api/helpers/caching.rb . The three retrieved official-source files have verified Git blob IDs and SHA-256 hashes in results/gitlab-readback-source-v1/source.json. They were not extracted from the packaged image, so exact packaged-byte equivalence is not established here.

The archives do not contain request timestamps, effective runtime cache keys, cache-hit telemetry or an intervention that isolates caching. Project cache-key changes, invalidation and process timing were not traced. Therefore this is a source-supported hypothesis, not a confirmed root cause, measured 30-second delay, or newly established GitLab defect. A later successful snapshot is not proof that the original assertion was valid or that all intermediate state was correct.

For any future design, read-only observers must be evaluated for their effect on cached responses. Merely adding arbitrary sleep or retry-until-pass would change the endpoint without demonstrating its validity. A candidate measurement protocol would predefine a time horizon, retain every observation with monotonic timestamps, bind reads to the write's commit identity, and distinguish transient visibility, persistent mismatch and unresolved observation. It would require independent qualification before a new scientific freeze, use the same information and observation policy across all arms, and retain the current failures. No such new execution or repaired cohort is authorized or launched by this diagnostic.
