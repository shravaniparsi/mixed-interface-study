# SeatSurfing warm checkpoint preparation v2

Supersedes v1 for capture lifecycle. The stopped-capture component cannot preserve the warm application process and native editor needed by the registered comparison. No runtime used v1, so this correction precedes application outcomes. Retain v1 and its tests as historical preparation; the future qualification recipe must use v2.

Capture requires the application and browser to be running but paused, with PostgreSQL running and unpaused. The enclosing worker must first settle all observed requests/operations, capture native browser storage, pause both containers, and retain the live observations proving those steps. This component does not itself pause/resume containers. During database capture, only idle, transaction-free connections from the original seatsurfing account on loopback are admitted; any other session fails the guard. Paused process identity, original images, network namespace, labels and all existing database scope checks remain enforced. Capture brackets the dump with identical fingerprints.

After capture, the future worker must resume the same original process/browser and run the warm native continuation without reload or reconstruction. Subsequent restored branches must stop both containers and satisfy the stricter zero-other-database-sessions guard before database restoration. The complete dump, schema/configuration/sequence checks, fixed JWT files and original browser-storage bytes are unchanged. This prepares a meaningful warm reference; it does not establish warm-versus-restored equivalence until exercised and checked in a real runtime.

Restore now requires the expected manifest SHA256 from the retained capture result, supplied explicitly by the coordinator. Verify that hash before reading the inventory and require the exact five retained members. Do not trust a modified manifest to redefine its own evidence. Verify all file and database-baseline identities before restore; only then invoke the atomic PostgreSQL restore and full equality check. The same read-only root/key mount constraints and private sealed-evidence requirements from v1 remain in force.

Eleven synthetic database-guard tests cover paused capture, rejection of stopped capture and rejection of paused restore in addition to prior guards. Nine synthetic bundle tests include changed manifest and incomplete inventory rejection before database mutation. These tests mock Docker/database state; no actual pause, dump, restore, browser or application execution occurred. Startup effects, process/network quiescence, browser restoration and warm/restored ordinary equivalence remain pending runtime gates.
