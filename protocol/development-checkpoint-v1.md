Add only a filesystem snapshot repository mount to Elasticsearch, not business configuration changes. Preserve original application startup reindex and cache behavior. Stop the application gracefully (30-second deadline), then copy its complete H2 directory and hash every file. Do not copy live H2 files. Create a supported Elasticsearch snapshot after application termination, require SUCCESS and no failed shards. In each of two fixed restoration phases, delete only the explicitly enumerated isolated snapshot indexes, restore the same snapshot without partial recovery, replace the stopped H2 directory with the checkpoint, and verify byte identity before application startup. Unexpected/system index names halt before deletion. Start the original application, repeat native login/readback/editor/search observations, then stop. No raw application logs, H2 files, snapshot data or tokens are published; retain their scoped hashes and reindex/mail-failure indicators. Browser screenshots contain synthetic UI data only.

Compare each restored phase with the seed: full returned admin record, actor projection, all observed native controls, save availability, logical index contents and counts. Record every equality separately, including false results. Three observed phases means measurement completed, not that continuation equivalence is qualified. Relational-byte identity is checked before startup; this does not claim that restart leaves bytes unchanged. Logical search equality excludes index UUIDs, sequence numbers and caches, which must not be described as equal. Fresh native logins do not clone browser sessions. No API or native update is executed, so successful observations cannot establish edit-outcome equivalence or rule out restart masking. This necessary engineering gate is not a replacement for the later competent continuation comparison or independent evaluation.
