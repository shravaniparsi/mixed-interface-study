# Development workflow ordering v1

Published after root README/deployment reconnaissance and path-tree inspection, but before acquiring the first candidate's detailed admin endpoint documentation or handlers in wave 2. That earlier exposure is retained in the wave-1 record. This instantiates within-project selection for the approved editability design; it does not authorize runtime or select mutations.

For each development candidate in its fixed repository order, enumerate original documented API create operations that produce persistent named entities, retaining the inventory and exclusion reasons. Sort by UTF-8 canonical endpoint path, then HTTP method; parameter placeholders retain their documented spelling. Aliases of the same operation constitute one workflow and use the first sorted path. Where original documentation is insufficient, use the original routing inventory and label that basis explicitly. Do not silently restrict the inventory to the first convenient entity.

Map candidates in that order against the existing gates: native creation and editor, stable-ID readback, two independent editable scalar text properties, same actor, local synthetic operation and original executable provenance. Unsupported fields or operations remain visible. Do not call a later workflow the first eligible while earlier candidates remain unresolved. One workflow per repository, at most the first two source-eligible development repositories under the fixed split. Development outcomes cannot promote replacement workflows or repositories.

The documented endpoint inventory is a feasibility screen, not a claim of exhaustive application functionality. Unadvertised or unsupported operations outside the bounded mapped inventory do not become negative scientific cases. Preserve the existing per-project path/byte budgets; no additional source request is implied. Each later wave must name the exact dependency paths, revisions and purpose before acquisition. Freeze the full recipe, literal inputs, baseline coverage, engineering effort limit and runtime qualification budget before running any application.

Evaluate this rule during development and freeze the final evaluation procedure before acquiring evaluation source. Any development amendment must identify what prompted it and preserve earlier decisions; do not change evaluation rules after outcomes.
