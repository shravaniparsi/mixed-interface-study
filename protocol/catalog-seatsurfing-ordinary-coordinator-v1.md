# SeatSurfing ordinary coordinator v1: producer stage

The coordinator connects the existing original native browser, isolated API worker, lifecycle, actor acquisition and complete database comparators. It has no CLI dispatcher and cannot start a registered application qualification by itself. It consumes an already built/provisioned fixture and leaves it available to the enclosing checkpoint/continuation/evidence-retention sequence. No scientific case or application attempt is executed by this preparation.

For each of the two prescheduled ordinary edits, the enclosing job must provide a fresh original fixture. The producer stage executes this sequence exactly once:

1. Launch the original native worker, await the same startup handle, log in through the native form and capture original session storage.
2. Pause the same browser/application, verify the original actor against fresh database evidence and capture complete pre-creation state.
3. Record a creation-window start before resume, create the ordinary native reference through its original form, pause, record the end, capture full state and require exactly the native insert plus bounded selected-session activity.
4. Record a second window before resume, create the independent API target using original captured credentials, pause, record the end and require exactly its insert plus bounded selected-session activity. Compare both complete inserted rows, mapping only their distinct generated IDs.
5. Record a third window before resume and open the API-created target in the original browser session. The browser independently binds the actual native/API producer HTTP evidence and complete payloads. Capture the loaded editor storage/network, pause, verify unchanged actor continuity, and capture full database state. Require that opening the original editor changed only the source-defined bounded session activity.
6. Retain the same paused original browser/application and the untouched warm editor for joint checkpoint capture and the original warm scalar edit. The stage does not replace the browser or issue that edit itself.

All complete snapshots, comparison results, actor evidence, worker artifacts, API evidence and lifecycle observations remain private retained files. The original sample location and all other data remain covered by complete-state equality. Five native worker commands are consumed by this stage; the sixth is reserved for the warm edit. Short observation timeouts re-observe the same pending browser command within its original deadline, never resend it or launch another browser. Any stage failure prevents replay and retains a failed-stage report. The parent owns bounded cleanup even when a stage fails with processes paused or an API container pending.

Four tests exercise same-handle timeout observation, deadline exhaustion, the connected producer sequence with real full-state comparators, and an unrelated database mutation that stops execution before opening the target. Runtime boundaries are mocked; no application or database is started. These tests establish sequencing and rejection behavior only.

Outstanding before dispatch: joint checkpoint capture with evidence-derived prerequisites, original warm edit, stopped restoration and restart qualification, restored native/API continuations, current API actor/transport checks, complete request/post-state comparisons, source/runtime inventory binding, encrypted evidence retention, parent cleanup/deadlines and immutable executable workflow registration. A successful producer stage alone is not application qualification or a research finding.

## Connected checkpoint and original warm edit

After the producer stage, checkpoint capture requires the same paused process identities and a second complete row capture identical to the recorded warm state. Original storage bytes must match both the worker's retained bytes and its hash; original network bytes must match the retained trace hash and events. Browser pending-request and response-capture counts must be zero. Actor acquisition provenance must be verified, both captured credential hashes must match the original actor continuity, session/Cache Storage must remain empty, and the original access-token lifetime must still exceed two minutes. The settled network observation must be no older than sixty seconds at proof construction. No stale observation is retried to obtain a passing checkpoint.

The legacy joint-helper field `application_operations_settled` has an explicit operational scope here: observed network completion plus idle transaction-free database connections and unchanged full state under paused application/browser processes. The report records that scope and explicitly records `pending_application_tasks_proven_absent=false`. This does not prove that arbitrary background goroutines or timers have no queued work. The original warm-versus-restored ordinary comparison remains mandatory to assess the restart effect; a successful dump alone cannot establish it. This prospective definition adds no excluded fields to database capture or restoration and does not turn latent-task uncertainty into scientific success.

The coordinator verifies the private signing-key hash against original provisioning, invokes the existing joint checkpoint exactly once, retains private subprocess output, binds the returned manifest hash to the actual manifest and requires the dump's baseline fingerprint to equal the complete warm row evidence. Failure makes the coordinator unavailable and prevents a warm edit or replay. The parent retains responsibility for the enclosing job deadline and cleanup if a subprocess exceeds its bound.

Only after successful joint capture may the coordinator resume the original application/browser and issue its sixth and final native command: the prescheduled unrelated scalar edit. It pauses the same processes again, compares complete post-state against the warm baseline using the prospectively recorded operation window, and independently verifies the unchanged actor with fresh database evidence. It retains the full native network/request result for subsequent comparison. It does not yet classify request equality, restoration equivalence or application qualification.

Eleven coordinator tests now cover producer sequencing, five checkpoint-proof failure groups, the original warm edit, and joint capture with both matching and deliberately changed dump baselines. Runtime boundaries remain mocked. Nine existing joint-checkpoint tests also pass. No application, original schema or scientific case is executed by these tests. Stopped restoration/restart branches, API actor/transport checks, complete request comparison integration and enclosing encrypted retention/cleanup/registration remain outstanding.

## Connected stopped restoration and restored native branch

After the original warm edit, the coordinator explicitly resumes and closes the original browser worker so it can retain its final network trace, then stops the application. The lifecycle guard requires actual stopped application/browser containers and zero other database connections. Missing final network evidence, failed captures or pending requests prevent restoration. The stop observation retains the original checkpoint/storage/network bindings and actual stopped identities; it refers to the checkpoint credentials selected for restoration, not to a newly authenticated session.

The existing joint restore verifies the immutable manifest, signing keys, original browser storage and exact database restoration while both original processes remain stopped. The coordinator requires the returned storage hash to match the captured warm checkpoint and rechecks stopped container identities. Only after these checks may it remove the retained stopped browser container and start the same application container once. It observes the original health check for at most ninety one-second polls, with no repeated initialization or application restart on failure. These are bounded readiness observations, not new qualification attempts.

A new original browser context then receives the exact restored storage and original credentials. It performs no login: its only initial commands are open and capture. Application/database container identities must remain unchanged, and the database process identity must match the pre-restore process. A new lifecycle instance binds the legitimate new application/browser processes for subsequent pause/resume checks. The complete paused post-startup state must match the original warm baseline except for the prospectively bounded selected-session activity. The original actor, record readback and complete materialization inputs must also match the original warm editor before its unrelated scalar edit proceeds.

The restored native edit resumes those verified processes once, issues the original native scalar edit, pauses and compares complete post-state against the ORIGINAL warm baseline, not merely against another restored branch. Fresh database actor verification follows. Complete native request results remain retained for comparison with the independent API branch; this stage does not yet claim that comparison passed.

Thirteen coordinator tests now include actual sequencing through mocked restore/restart boundaries, refusal to remove or start anything after a failed restore, no re-login, and restored-edit comparison against the original baseline. The original database and joint-checkpoint guards are rerun separately. Runtime execution and encrypted retention remain unqualified. The independent restored API branch, transport/actor correspondence, integrated request matching, parent deadline/cleanup and immutable dispatch registration are still required.

## Connected independently loaded restored API branch

After the restored native edit, the coordinator repeats the same stopped-checkpoint restoration procedure for the prescheduled API branch. This is a planned branch from the original checkpoint, not an outcome-triggered retry. Both branches share one restore implementation with distinct retained artifact paths and strict predecessor phases.

The API branch starts a restored-storage browser context only to preserve the fixture's existing process/checkpoint guard interface. That context stays on `about:blank`: it receives no open, capture, login or edit command. All editor inputs come from the independently launched API loader. After that initial load, the coordinator pauses the fixture, compares complete database state with the original warm checkpoint, requires complete materialization-input equality and verifies the fresh API `/user/me` response. The API continuation then independently reloads its own source-defined inputs before writing; it does not reuse the initial loader's payload or a native request. This prescheduled extra load is retained and does not constitute another scientific case.

The fresh API actor check binds the actual GET response body/hash to the loader's self object, requires the original bearer-token hash, successful completed response, exact original user/organization, role IDs, effective permissions and authentication flags, and rejects cookies. Separately, the existing actor helper uses the explicitly identified original warm native trace plus fresh restored database evidence to verify signed credentials and unchanged session/roles. The API response is never converted to a fabricated native event. API self matching alone does not establish database identity.

Following the API edit, full persisted state is compared against the ORIGINAL warm baseline with the existing exact unrelated-edit and bounded-session-activity rules. Its independently loaded inputs and current API actor must still match. The complete API request envelopes and native results remain retained for integrated comparison; successful HTTP status alone is insufficient.

Seventeen coordinator tests now cover both branch selections, no native editor commands in the API branch, refusal to start after failed restore, API self identity/permission/hash failures and full-state API continuation comparison. All runtime boundaries are mocked. The integrated request comparator, broader transport qualification, enclosing deadline/cleanup/encrypted retention, original-schema execution and immutable dispatch registration remain outstanding; no application qualification is claimed.

## Integrated retained-request comparison

After all three ordinary branches complete, the coordinator compares the original warm native and restored native edit-result files independently against the retained API continuation worker result. Before invoking the offline comparator it requires each file to equal the corresponding observed branch result and the original storage hash to match the warm checkpoint. The comparator reads only bounded regular files, derives the original bearer credential from that storage, executes the existing complete main/ancillary comparison for both native branches, and records exact input-file hashes and its Node runtime version. It writes a new private result and emits no credential-bearing console output.

The parent requires successful comparison and exact agreement with its own four input hashes. Any changed artifact, wrong hash, mismatch or timeout stops the coordinator; no branch is repeated. The resulting phase is explicitly `ordinary_comparisons_complete_transport_unqualified`. It does not by itself qualify browser-added headers, original schema, the application, or the scientific study.

Validation now includes eighteen coordinator tests, with matching retained artifacts, changed native artifacts and changed comparator hashes. Eight JavaScript request-comparison tests include actual offline execution on synthetic files for both successful agreement and a deliberate restored-native payload mismatch. No application request is issued by these tests.
