# Username failed-write database diagnostic

This is a mechanism diagnostic for previously exposed RealWorld cases, not a replacement campaign, a new primary sample, or a completed continuation comparison. The halted identity ledger and its classifications remain unchanged. The selected null, 60-character and 61-character cases retain their exact development-registry payloads and policies.

Each case restores the same offline synthetic SQLite fixture containing one account and three articles. Before the prefix, immediately after its HTTP response (before any diagnostic API read), after backend teardown, and after a backend restart/readback, the runner creates a SQLite backup from an independent read-only connection with read_uncommitted disabled. Backups are retained unchanged and independently projected. They contain only task-generated fixture data, including its synthetic account credential hash; no real accounts or user data are used. The reported projection omits credentials.

The projection binds the stable user primary key, username/email/profile fields, three article primary keys/slugs/bodies, and their author foreign keys. It discovers the unique tables by required schema fields and rejects ambiguous or unexpected fixture populations. The verifier reopens every retained backup, checks hashes and projections, and reconstructs whether the requested username is present after the response and survives a process restart. Selected-column equality is not a claim of whole-database equality.

HTTP requests and responses, ordered backup events, process stop/restart boundaries, server logs, fixture restore hashes, source snapshots, pinned backend revision and installed dependencies are retained. Readbacks use the same authenticated synthetic actor. No recovery write or schema change is made. A server error alone establishes neither rollback nor commit; database evidence and restart persistence are reported separately. API readback failures and unresolved acceptance requirements remain explicit regardless of the stored value.

There is one diagnostic execution per selected case, no automatic retries, and no attempt pooling. On a runner error, all completed and partial evidence is retained and the diagnostic remains incomplete. The backend dependency lock matches the existing study; the frontend and browser are not involved. Conclusions are limited to this pinned SQLite deployment. Generalization to production databases or other backends requires separate evidence.
