# Prospective full-frame instruction eligibility screen

Scope: all 175 task instructions archived at TheAgentCompany/TheAgentCompany revision 98b68ef82a47690c316f42fddb05baafaab56851, with an exact image-catalog match. Freeze this document before semantic review of the remaining task instructions. This is a design screen, not registration of a scientific runtime experiment.

Prior exposure: the complete instruction archive has been processed by lexical inventory; all 17 Plane-mentioned instructions and admin-arrange-meeting-rooms were read by the analyst. The Plane project/membership/assignment task prompted this fuller audit. Consequently this rule is prospectively fixed relative to the remaining review and all runtime outcomes, but is not independent of every task description. No task grader, checkpoint rubric, solution or scientific task outcome has been inspected. Infrastructure availability checks are separate from semantic eligibility. The current coding is by one analyst and must not be described as independent adjudication.

Question: does a task explicitly require a persistent web-application state change followed by an operation that uses that newly produced entity or changed state? This identifies potential API-producer/native-consumer workflows. It does not establish API support, native realizability, useful baseline separation, defects or novelty.

Assign exactly one primary code to every task, retaining an instruction-grounded explanation and, for possible chains, the producer, consumer and dependency. Use these codes in priority order:

1. `explicit_chain`: the instructions explicitly require creating or modifying persistent web-application state, then a distinct requested operation consuming that entity/state. Examples of abstract structures include creating a container then adding its contents, creating an object then editing/deleting it, or uploading an artifact then sharing the resulting application link. Merely reading an existing object before a single update does not qualify.
2. `conditional_chain`: such a chain is explicitly requested only under a condition or coworker response. Record that condition; do not assume it occurs.
3. `ambiguous_chain`: the instruction could imply a qualifying dependency but does not specify it sufficiently, or has conflicting application/operation requirements. Do not repair or invent steps.
4. `write_without_produced_state_consumer`: one or more writes occur, but no explicit later operation consumes their new application state. Parallel writes to existing entities and reading from one system before a single write to another belong here.
5. `no_web_state_write`: reading, analysis, local code/file production or computation without a persistent web-application write. Creating a local artifact and uploading it once is a single web write, not a web producer/consumer chain.

Record separately the application names, any requested coworker response, and any unresolved interpretation. A chat message merely announcing completion does not by itself consume new state; a message explicitly sharing a newly produced entity's URL or identifier can. This distinction must be explained per task. A chain can be cross-application; do not restrict eligibility to Plane or familiar applications. Implicit navigation and assertion/readback invented by the experimenter are not requested consumer operations. Do not decompose a chain into multiple independent samples.

Review every task in lexical task-name order. Retain all codes, not just eligible-looking tasks. Do not exclude tasks based on fault likelihood, known validation behavior or runtime convenience. Infrastructure, paid-NPC requirements, supported API operations and native representability are later feasibility fields and cannot silently remove tasks from the semantic denominator. No new task instructions, payloads or mutations may be added to improve the yield of this screen.

After coding, report counts and cross-application/operation/dependency diversity at the task and workflow-family levels separately. Group substantively equivalent chains before interpreting sample size; task count is not independent workflow count. Do not claim statistical power or selector identifiability from lexical application counts. Determine whether there is sufficient structural diversity to compare the intended method against competent information-matched baselines before registering any runtime schedule. If the frame is insufficient, record that result rather than implementing the one most convenient task or seeking positive outcomes elsewhere.

No scientific execution, paid model call, source-built service adaptation, or manuscript effectiveness claim is registered by this screen. Those require a subsequent justified contribution/design decision. The previous cohorts remain closed.
