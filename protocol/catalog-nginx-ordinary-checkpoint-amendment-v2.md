# Prospective clarification: one warm checkpoint per ordinary edit kind

This amendment is published before any Nginx Proxy Manager application, schema or scientific outcome. No qualification attempt has been dispatched. It supersedes the cross-edit-kind "same checkpoint" wording in catalog-nginx-input-freeze-v1.md, the ordinary_policy field of the immutable v1 input schedule, and the fixture discussion in catalog-nginx-native-schema-controls-v1.md. The original artifacts remain retained. All nine producer inputs, their values, mutation order, unrelated edits, baselines, per-project attempt limits and job/time bounds remain unchanged.

The ordinary producer input requires two independent continuation comparisons: an address edit and a password edit. Executing the first warm edit changes the database and audit history. Returning to the original state by restarting/restoring the application would make a second reference a restored reference; undoing the edit through the API would also change history. Neither establishes an untouched warm reference for the second edit.

Therefore instantiate two isolated ordinary-control scenarios inside the same bounded qualification job. Each scenario starts the same built original application with the same synthetic fixture values, performs the API/native producer controls, creates its own ordinary subject, and captures its own checkpoint while the original process remains warm. For that edit kind, compare the warm native continuation, restored native continuation and restored information-matched API continuation from that exact checkpoint, with the same actor/token/key and complete relevant starting state. Repeat the complete sequence in a fresh isolated instance for the other edit kind. Build/provision shared immutable artifacts once; do not transfer mutable state or an actor token between the two fresh instances.

Generated IDs, timestamps and keys are not asserted equal between the two independently bootstrapped scenarios. Exact matching is within each scenario's three branches. Both scenarios are mandatory and must pass within the same maximum 30-minute qualification job; no additional job or timeout extension follows if they do not fit. A narrowly permitted second qualification attempt remains subject to the existing correction rules. The shared ordinary scientific input, if eventually dispatched, likewise contains the two scenarios in its single 15-minute job. There remain at most nine scientific jobs and nine producer input definitions, with all fixture/API calls reported separately.

This correction preserves both warm references and complete matched branch state. It is a pre-execution design correction, not a response to an application finding and not evidence of successful qualification. The full runtime orchestration and remaining state predicates must still be registered before dispatch.
