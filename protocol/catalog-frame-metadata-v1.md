# Curated catalog frame: metadata feasibility only

Candidate sampling source: awesome-selfhosted/awesome-selfhosted-data, a curated software catalog rather than another star-ranked application query. Its schema, license and suitability are not assumed. This stage checks the catalog itself; it does not select applications, inspect their implementation, establish independence or reopen any closed frame. A catalog inclusion bias and any framework/deployment filter must be disclosed in a later sampling registration.

Before external requests, build a bounded reference index from tracked Git blobs at the current study HEAD. Scan declared text extensions, maximum8MiB per blob and512MiB total in UTF-8 path order. Record every tracked file's blob identity, size and disposition, including nontext, oversized, missing and budget-skipped files. Extract GitHub owner/repository references from URLs and explicit repository/full_name/repo JSON-style fields. Preserve referring paths; normalize case and .git suffixes. This is a reference-exposure index, not proof of implementation exposure, complete historical coverage, absent model-training exposure or family independence. Prior reference/audit artifacts in the snapshot are included; deleted history or untracked sources are not silently certified absent.

Then make at most five sequential GitHub API requests, each30seconds within a total120-second deadline, without retries or alternatives: repository metadata; its declared default-branch ref; recursive tree at that pinned SHA; the first lexicographically ordered root README candidate; and the first lexicographically ordered root license candidate. README names are README, README.md, README.rst, README.txt (case-insensitive); license names are LICENSE, LICENSE.md, LICENSE.txt, COPYING. Missing root files are recorded, not replaced by other paths. Metadata/ref responses≤1MiB, tree≤8MiB and blob envelopes≤256KiB, decoded root text≤128KiB. Require an untruncated tree and verify root Git blob identities.

Retain raw public catalog API metadata, root-document hashes and any errors. Do not retrieve software entry contents, application repositories, issues, tests or fixes, catalog archives/layers, or execute repository code. A root document may incidentally mention outcomes; log any such exposure before later selection. No installations, application jobs, paid service/model calls or external messages. Existing $100 ceiling remains.

After inspection, decide whether this catalog offers a documented, auditable metadata population and what a prospective selection rule would require. No sampling seed, inclusion rule or target count is inferred after viewing application outcomes. Any actual software metadata collection and application selection requires a separately published fixed rule, denominator, overlap treatment and acquisition bound. If unsuitable, retain that result rather than substituting another catalog under this schedule.
