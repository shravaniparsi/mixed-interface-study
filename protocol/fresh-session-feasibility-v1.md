# Fresh-session editability: feasibility protocol v1

Status: prospective development feasibility, authorized by the user's explicit fresh-session choice. This is a separate protocol, not an amendment that reopens the closed six-slot evaluation. No confirmatory evaluation, defect search or paper-ready evidence is authorized here.

## Question and changed scope

Can a record created through the original API be opened by the same actor in a new native browser context, edited through original controls, and verified independently in persistent state? Can this process be repeated from isolated clean starts with interpretable request/state evidence?

Every native continuation starts in a new browser context. This does not reproduce an already-open session or claim equality of opaque process/browser heaps. Persistence, authentication, loaded record, user-visible fields and event/request activity are observed explicitly. Process restart is an experimental initialization condition, not a proof of warm-state equivalence. Hidden-state uncertainty remains a limit on later causal claims.

G0: Publish this protocol, exposure record, exact identities and job/cost ledger. Confirm old evaluation closed and no overlapping experiment. Zero invalid-input runs.

G1: Inspect full build command chains, nested package scripts, Docker stages/entrypoints and runtime bootstrap before writing recipes. Classify expected generated file/manifest changes in advance. Preserve original and final package/lock/dependency inventories, including changes made by original build scripts. Use verified Git commits/trees/blob modes; API response root identifiers are not assumed tree hashes. Source/packaging tests must exercise real archive or Git tree fixtures, symlinks/modes, unsafe paths and meaningful tampering. Never patch original validation/business logic to pass.

G2: Complete both deployment recipes, ordinary-input manifests, browser/control adapters, persistent-state observers and independent result scorers. They must cover all required native/API actions before any application startup. Test failure classification and scorer refusal using fabricated evidence fixtures, not application defect inputs. Source inspection during this development phase is allowed and logged as exposure; it cannot be used to add systems or select failing inputs.

G3: Build or verify immutable runtime identities. A successful build is only a build result. Backend startup, frontend compatibility and authentication remain separate checks. Preserve diagnostics sufficient to identify exact failed file/check/command; absence of diagnostics is unavailable, not permission for a blind retry.

## Ordinary feasibility matrix (no defect search)

Freeze per-system valid native/API request bodies and replacement values from prior source-supported ordinary fixtures. Zipline retains all four previously mapped ordinary fields; Shlink retains longUrl and title. Do not import their old omission/null producer arrays. No missing/null/boundary/adversarial inputs. No real-user data, inter-user messaging or third-party requests; Shlink title resolution uses the existing local fixture server.

For each system:

A. Bootstrap a disposable original actor and empty application state with original supported configuration. Verify full relevant persistent stores, schema/sequences, files and cache/queue scope. No rows injected in place of original bootstrap. Record runtime identity and raw observations privately, publish redacted evidence.
B. Use native creation once and verify every chosen ordinary property independently; then use API creation and read back stable ID, actor and exact persisted property values. Verify original editor can load that record in a new context. Every selected field must support its frozen valid replacement and reset, with independent readback.
C. Run three prespecified repetitions from the same verified persistent root in isolated application instances. This is a reproducibility check, not three independent systems. Use the original runtime configuration, new browser contexts and original login/load in each branch. Within each repetition compare an untouched valid record continuation with a valid no-op repair (set the chosen target to its already-present ordinary value) followed by the same unrelated edit. Cover every target at least once; declare the complete branch matrix before startup. Balance branch order using a frozen seed and record it. Both branches should succeed with the same intended business-field change. This is a control for the proposed repair procedure, not evidence of repair benefit.
D. For each operation retain original request/response, independently observed persistent start/end and native form/control outcome. Observe auth/session bookkeeping and backend background activity. Specify source-supported timestamp/identity/derived-effect comparisons before outcomes, retain raw deltas, and reject unexplained effects. Never normalize away an observed failure after it occurs. Fresh session does not excuse unknown pending writes or unobserved queued effects. Bound settling by explicit owned-work completion evidence; silence alone is insufficient.
E. Test observation integrity without invalid app inputs: check deliberately corrupted copies of result evidence are rejected by the independent scorer. Prove target-record identity, intended edited value, invariant unrelated fields, no duplicate write and no external effects. Missing persistence evidence cannot be replaced by HTTP2xx, a toast or a screenshot.

Fresh contexts intentionally have new session identities; report this explicitly. The same application actor/privileges must be verified. Authentication side effects belong to the observed initialization condition. Do not assert byte-identical browser memory or cross-session credential equality. If unmeasured initialization variability prevents a defensible comparison, feasibility fails.

## Pass, stop and publication boundary

A system passes only if all required actions and all three repetitions pass independent scoring with complete required observations. Both systems must pass. Any failed or unavailable required gate means feasibility is not established. No average-success threshold, no excluded inconvenient repetitions, no extra substitutes.

A build/control failure is diagnosed once. Use the sole shared correction only for a documented eligible issue; record old and corrected evidence. Otherwise stop. When one system fails terminally, do not launch work on the other merely to fill a table. Preserve all progress and costs.

Required final report: per-system gate table; exact revisions/runtime/dependency manifests; recorded run IDs, durations and costs; every failure/unknown; requests, persistent state and control evidence; independent scorer output; exposure/sample limitations. Outcome is GO or NO-GO for designing evaluation, never Q1-ready.

Only after both pass: verify novelty against primary literature, specify credible original-schema and native-validation baselines, determine a scientifically justified sample/analysis and contribution threshold, then register a separate independent evaluation before outcomes. Original Swagger/OpenAPI dialects must be respected; no handler constraints smuggled into schema baselines. No claim about agent-model behavior without actual agent experiments. A successful feasibility study alone is not a journal contribution.
