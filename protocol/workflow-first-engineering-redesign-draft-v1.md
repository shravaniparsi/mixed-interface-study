# Workflow-first engineering redesign: decision draft

Status: design only. No new acquisition, runtime, resampling, reopened cohort or scientific input is registered here. The Q1 objective remains unmet. The closed studies retain their original denominators, stops and exposure records.

## Problem this design must solve

The previous procedure explored broad application/workspace entrypoints in breadth-first order under a 96-file cap. The retained Bichon graph places the native account create/edit components at positions 196 and 197, and the server API registry at 177. Faster Chat places the general API transport at 117. These are retrospective positions in an incomplete known graph, not predicted costs or independent validation. They show that file count and traversal order jointly prevented required bindings from being reached; they do not show that either application is intrinsically infeasible.

The contribution question remains whether native continuation adds information after accepted API production when persisted starting state, actor and edit serialization match a competent API continuation. More applications, an agent wrapper or additional passing harness tests do not establish that contribution.

## Separate development from evaluation

A future engineering pilot must use an explicitly exposed development system and ordinary input only. It cannot reopen or add results to a closed scientific cohort. Any later evaluation frame needs a separate exposure assessment, selection rule and immutable input freeze. No claim of unseen source, independent families or natural defects follows from a development pilot. The current two candidates cannot silently become a fresh independent cohort.

## Resolve one complete workflow instead of the whole application

Start from the original documented deployment and native route inventory. Apply a frozen route/resource eligibility order before looking for discrepancies. Trace the selected native producer and editor through their event handlers, full serializers, transport and corresponding supported API operations; then resolve their original schema, actor initialization, readback and persistent/background state. Earlier-route exclusions require recorded evidence. Do not recursively expand every public module or unrelated route solely because it appears in a workspace export. Shared helpers are followed when they affect the selected action or controls.

A dependency is resolved by adequate original documentation, exact source, or qualified ordinary runtime evidence as appropriate to the claim; reading every implementation file is not itself a validity requirement. Conversely, source inspection alone does not establish runtime identity, actionability, persistence or isolation. A schema must remain original, and actual native serialization must be supplied to the API comparator. Feature-name guesses, reconstructed frontend rules and direct database edits cannot substitute for supported actions.

## Admission remains demanding

Before scientific inputs: verify immutable application/package identity, native actor setup, valid native create/edit, supported JSON producer/update/readback, original schema availability/dialect, complete relevant persistence and browser state, and ordinary native/native, API/native and API/API controls. Establish exact checkpoint equivalence and account for background writers and observation side effects. Endpoint-level failure or a selector problem is not a native-only defect. If qualification fails, retain the failure and stop within the registered numeric budget.

The previous omission/null input policy and clustered interpretation remain candidates, not automatically valid for a new frame. No fixed number of positive findings is a success criterion. A null incremental result requires enough qualified comparisons to interpret; missing comparisons cannot stand in for it.

## Required before this draft can authorize work

A concrete pilot registration must name one development workflow, its exposure, exact original deployment assets and source/runtime binding, the claim-specific dependency scope, numeric source-byte/request and wall-clock/job budgets including failures, and terminal failure classifications. A later independent evaluation registration must define its population, competent baselines, sampling/eligibility, input policy, causal checks, uncertainty reporting and interpretable null outcome. Choose these from the scientific question and available resources, not by increasing a cap until a favored application passes.

No defensible independent evaluation frame or qualifying pilot is established by this draft. Therefore do not fetch another cohort or resume the stopped Bichon/Faster Chat collections on its authority. The next decision must be whether a concrete pilot can meet the admission requirements within the existing resources; if not, report that the proposed empirical contribution cannot currently be completed.
