## What failed and what must change before spending again

Flagsmith exhausted preparation time after build; Shlink stopped on unexplained source verification; Relaticle failed its original SQLite migration; Komga's observer failed; Snipo required explicitly unsupported FTS5 state; Donetick's harness mishandled original build behavior. These are distinct mechanisms. More retries would not establish scientific validity.

Planning should establish executable infrastructure in a declared development phase before freezing a confirmatory sample. Inspect complete original build scripts, including nested commands, and retain both initial and final dependency manifests. Preserve actionable failure context. A deployment may be operationally unsupported without being a defective application.

The exact warm-state restoration requirement demands equivalence of server/client memory, active event streams, background work and persistent data. Existing database snapshots and browser reloads do not prove that. Do not quietly replace that claim with persistent-state equality.

## Scope decision required

Option A: a separately registered fresh-session editability study. Question: after an API creates a persistent record, can the same actor open it in a new native browser session and perform a predefined unrelated edit; does a prespecified field repair improve that outcome? This preserves the API-to-native-workflow problem, but changes the session condition. It does not answer whether an already-open agent/browser session can be restored exactly.

Fresh-session pairs would use isolated restored application instances, original native login/load, matched persisted inputs and prospectively specified observations. Randomization/repetition would address stochastic initialization rather than assert byte-identical hidden memory. Independence units remain application/workflow mechanisms, never repeated runs. Any causal claim must state its initialization assumptions and demonstrate that the repair is the only intended treatment difference. This design still needs validation; it is not automatically cheaper or publishable.

Option B: retain exact warm-state recovery. Before any further application study, demonstrate a general full-process/browser checkpoint mechanism with relevant queue/event fidelity on development systems. Do not promise this within the current budget. A failure to establish it is a stop condition, not grounds to soften the requirement after outcomes.

Option C: stop this empirical direction and reassess the research question using the preserved feasibility result. Do not manufacture a Q1 paper from infrastructure failures.
