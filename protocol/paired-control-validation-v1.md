# Paired-control runtime validation v1

Scope: an engineering validation of the existing ordinary Quartz controls. No mutation or previously unexecuted boundary case is included. This validation does not complete the eight-workflow primary freeze or evaluate diagnostic/selector effectiveness.

Use the four `route_only` entries from the unchanged Quartz v2 registry. Form two pairs distinguished by producer interface. Execute the API-producer pair with API then UI continuation, followed by the UI-producer pair with UI then API continuation. Every branch starts a fresh JVM and empty RAM store. The existing source-pinned adapter performs the registered description edit and records its ordinary shared verification probes.

Before launching the application, save the exact ordered case IDs, pair membership, source/registry hashes, effective command/options and supplied environment/browser sidecars. The ordered-case input must contain exactly the four registered controls once each. The registry runner must reject a mutation, duplicate, missing control or use of an ordered-control list with `mode=all`.

For each pair, verify independently recorded evidence directories, identical registered producer input and intended consumer input, actor equality, equivalent initial state and accepted post-prefix state, and actual bound consumer intent. Check source-pinned component extraction independently of aggregate status. Retain shared API readback and supplementary UI observations as separate components. A missing, rejected, inconsistent, timed-out or unfinished branch cannot yield a valid clean pair.

The wrapper records a 75-second per-case timeout and a 330-second campaign deadline, followed by up to 110 seconds for runner shutdown and five seconds for hard-kill confirmation. The existing runner may wait for the active case's escalation, so this is not a claim of prompt cancellation. The outer CI process cap is 480 seconds. All effective values are saved in the plan. Any interruption, nonzero exit, unconfirmed cleanup, prefix disagreement or incomplete evidence leaves the attempt invalid. Do not resume a partially completed control attempt or combine it with a later run. Preserve unsuccessful attempts and corrections; after a correction, execute a fresh complete control attempt.

The summary reports control-pair validity, input/state/actor/binding comparisons, component observations and recorded costs. It does not assign defects, root causes or detection overlap. Four control executions remain one workflow template in one application. Actual deadline-path validation and budgeted selection remain separate engineering requirements.

Run the hosted `quartz-paired-controls` suite after unit and provenance checks pass. Preserve its full artifact locally before the seven-day Actions retention expires. Record the source commit and CI environment; do not pool its timing with previous local or hosted batches.
