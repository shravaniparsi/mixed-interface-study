# Fixed catalog cohort: application qualification and experiment gates v1

## Cohort and contribution question

Use exactly the twelve repositories in manifests/catalog-cohort-v1.json, in its recorded order. Do not replace failures, change selection filters, revisit closed frames or count owner groups as established independent lineages. The question is whether native continuation adds observable information after API production beyond HTTP, original-schema and information-matched API-continuation checks, and what proportion of this fixed cohort can support that comparison. Qualified null results and qualification failures change feasibility and scope conclusions; no positive-defect count is a success criterion. This is a curated, Docker-labelled, reference-screened cohort, not a population-prevalence or universal generalization claim.

## Metadata and revision acquisition

For each selected repository allow exactly three sequential GitHub API requests: repository metadata, declared default-branch ref, and recursive tree at that SHA. Limits: 30 seconds/request, 90 seconds/repository, metadata/ref <=1 MiB each, tree <=8 MiB. No retry, alternative ref, substitute repository or automatic clone. Record non-200, timeout, missing/default-ref failure or truncated tree as unavailable for this stage. Other projects continue in fixed order. Require repository canonical full_name to match the selected identity case-insensitively; a redirect/rename is held for explicit alias audit, not silently followed into independence. Preserve fork, parent/source, archived and disabled metadata. Record all requested endpoints, byte/hash identities and deviations.

A repository marked fork, sharing parent/source/owner with an earlier exposed or selected family, or identified as a renamed prior project is quarantined or grouped conservatively; unresolved ancestry remains explicitly unresolved. No new parent-source download in this stage. Historical raw-reference gaps remain unresolved; source-reviewed observations cannot later be described as blind or untouched. Do not fetch issue/PR discussions, changelogs or bug fixes to choose targets.

## Source acquisition and eligibility order

After metadata is retained, publish a per-project path schedule derived from its pinned tree before each source wave. Maximum 256 unique blobs and 8 MiB decoded per project, 256 KiB/file, 512 KiB envelope, 30 seconds/request, no retry or ref change. Failures consume scheduled slots. Root README/license/build/deployment metadata counts toward this same cap. No archive, package installation, image pull or execution until runtime qualification is separately instantiated. Do not chase every transitive import: acquire the producer handler, original native form/model, update handler/serializer, validation/default helpers, API schema, relevant persistence and authentication/bootstrap contracts needed for one complete candidate mapping. Unsupported essential branches end that candidate rather than being guessed.

Enumerate native create-and-edit workflow candidates from documented UI actions and source tree routes, ordered by UTF-8 native create-form/route path then entity identifier. Retain considered candidates and rejection reasons. Choose the first eligible workflow under that order; retain earlier unresolved candidates as unresolved, not absent. Eligibility requires a locally hosted browser UI, programmatic JSON record creation and update, persistent readback by stable identifier, same locally bootstrapped actor/permissions, and an editor containing at least two independently editable scalar text properties. The mutation target must be one editable text property and the unrelated edit a different property whose semantics do not depend on the target. Exclude flows requiring real external accounts, paid services, hardware/cameras, GPU inference, actual clinical/customer data, file uploads, inter-user messages, financial transactions or third-party network side effects. Synthetic fixtures only. A browser-only local store without a server mutation API is ineligible. Local supporting services are allowed within standard hosted-runner resources. Catalog descriptions alone cannot establish these capabilities.

Freeze the first eligible workflow before altered outcomes; no substitution after its runtime/control failure. Workflow paths, considered ordering and source completeness are reviewable selection evidence, not a claim of exhaustive application coverage. If the acquisition cap prevents a complete map, report source-mapping unavailable with pending essentials. An earlier unresolved candidate prevents claiming that a later candidate was demonstrably first eligible; any later use must be separately labelled a deterministic first-qualified mapping and the unresolved prefix retained.

## Fixed experiment design to instantiate before execution

Per qualified workflow, freeze complete original-source producer/update contracts, actor, all native controls, JSON defaults/coercions/omissions, and persisted readback according to continuation-request-matching-policy-v2.md. H records response and persistence; S validates only against the original API schema using a pinned dialect-compatible implementation, reporting missing/unsupported checks as unavailable; A uses the complete source-materialized matching update and readback; U uses ordinary original browser controls. Do not weaken source-aware/native-rule replay to manufacture superiority. Any D implementation is a separate versioned baseline with frozen coverage; H/S/A/U findings alone do not demonstrate an algorithmic advantage over D.

Choose the first four supported scalar text producer properties in UTF-8 JSON-pointer order that have an unrelated editable property. For each, preschedule omission and explicit null plus one shared ordinary control, maximum nine producer inputs. Preserve classes deemed unsupported before outcomes. The unrelated property is the first other eligible text property by JSON-pointer order; its fixed benign replacement and ordinary values must be frozen before outcomes. Use no added type/length/boundary variants after seeing results. Cases are correlated observations; distinct violated semantic obligations, projects and lineage groups are separately reported. A missing-property and null manifestation of the same obligation do not become two independent defects.

An ordinary native producer and API producer must first support the same intended record and native editor. Then qualify the source-materialized complete ordinary update against an actual emitted native request. Warm ordinary continuation, a restored native branch and a restored API branch must be prescheduled. Check same full relevant starting state and actor, native actionability, complete request equality and persisted outcome; never infer warm equivalence solely from two matching restores. State restoration must use supported database/storage procedures, account for startup reindex/cache effects, and publish any permitted generated/audit-field differences and operation-specific checks before scientific outcomes. A generic snapshot recipe is not presumed valid across applications.

For each accepted altered producer state, preserve its original creation/readback, then compare native and API continuation from the same qualified restored state. Native-blocked cases require applicable counterfactual source materialization; if that mapping cannot be established, retain U but mark incremental U-versus-A unavailable. Do not force-enable Save, inject validity, programmatically submit or modify the application. Reject ambiguous controls, mismatched payloads/states and unsuccessful ordinary branches as scientific evidence; retain them as qualification failures. Do not define success by HTTP status alone or silently remove normalization differences. Record legitimate contract differences, normalization, native incompatibility, backend rejection and instrument/setup failure separately.

## Runtime and stopping envelope

Use standard free public GitHub Actions runners only, no larger runners, paid models or local application execution. Preserve the existing $100 ceiling and terminal timing records without equating reported Actions billable milliseconds with total cost. At most two qualification jobs of <=30 minutes per selected project: one original attempt and one narrowly documented infrastructure/instrument correction that cannot change workflow, scientific inputs or outcome criteria. No second correction or alternate workflow after failure. No application job starts before pinned executable/image provenance, local-only networking boundaries, supported state restoration, native browser/tool versions and per-project commands are published. Image tags alone are insufficient version evidence; unsupported image-to-source mapping is unavailable.

For a qualified workflow allow at most nine scientific jobs of <=15 minutes each, one per prescheduled input, each containing its matched branches and checks. Maximum two application jobs concurrently. No retries after scientific outcomes, no finding-driven repair runs or input additions; partial/missing outputs stay missing. Unused slots do not transfer between projects or phases. Stop at these limits even if the evidence is negative or insufficient. A target-only repair or extra causal intervention would need prospective justification before outcomes; none is authorized by this registration.

## Reporting and gates

Retain the denominator of twelve selected owner groups, all exclusions, ancestry/overlap dispositions, source-mapping failures, executable-provenance failures, qualification attempts, ordinary-control failures, schema/baseline unavailability, all prescheduled inputs and branch outcomes. Report project/workflow/obligation counts separately from input/branch counts. No confidence interval over correlated variants can stand in for independent-project evidence. Source-derived rule relevance is a hypothesis until supported by actual state and actionability observations; admitted native incompatibilities do not automatically establish a software bug or Q1 contribution.

Metadata requests are authorized by this published protocol. Each source wave and runtime/scientific job still requires its concrete schedule or instantiated recipe to be published before execution; these are execution records under this fixed design, not opportunities to change its rules. If all feasible projects yield a well-qualified null, assess that result honestly against the contribution question. If qualification fails broadly, report the bounded frame's feasibility limits without opening another cohort to search for positives.
