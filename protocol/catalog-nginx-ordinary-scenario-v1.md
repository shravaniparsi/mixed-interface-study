# One ordinary scenario integration

The scenario runner connects the existing components against an already provisioned original runtime. It neither dispatches a job nor starts a new application container. The parent must supply verified source/build/browser identities, the registered isolated network and immutable original image, private mounts, a single shared deadline, the published complete registration and cleanup. The two independent ordinary scenarios remain required under the v2 checkpoint amendment; this module implements one scenario, not an extra attempt.

Observe the existing container's original immediate logrotate and certificate completion markers within a 120-second startup bound. Repeated observations use the same container and startup identity, without restart or initialization retries. Retain both log streams privately, inspect the original-driver database and require the empty certificate/proxy fixture. Startup rewrite windows derive from authoritative Docker StartedAt, not from when the observer first polls.

Use one original native login. Create the ordinary API seed, ordinary native fixture and ordinary API subject in that order. Require three distinct stable IDs, successful readbacks and original producer-schema acceptance. Inspect actual persisted names, booleans, owner, deletion flag, auth username/password and client directive/address for all three records. Require the original actor email to identify exactly one persisted user. Do not reconstruct stored credentials from producer intent.

Capture original browser storage and the coordinated database/mounted-files checkpoint. Reinspect the warm branch after capture and require exact database/inventory agreement. Run warm native, restored native, then restored API updates. Restore the same immutable checkpoint before each restored branch, explicitly start the same original container, observe the new startup, restore the original browser storage and require registered-root/database restart equivalence and the same expanded entity readback. No new login is admitted.

For each branch, retain the exact request and original response, run the original schema validator on the actual wire body in the installed application runtime, observe database/runtime/access-file effects, and invoke the integrated operation-delta checker. Require complete JSON update method/path/body, authorization and content type to agree across branches, and the full checked database outcomes to agree apart from operation-bounded original timestamps. Require backend and nginx master identities to remain continuous within a branch; only an explicit observed startup resets that comparison. Runtime observer output, Docker metadata/root-layer diffs, database snapshots, access files, logs and browser envelopes remain private.

The browser transport preserves one pending command across observation timeouts. It never resends a mutation or replaces a worker. Every new command is bounded by the parent's remaining deadline and the existing command deadline. Any failed step propagates immediately and prevents later branches. There is no internal repair or rerun path. The parent must retain a failure summary and perform cleanup even on exceptions.

A completed sequence returns `ordinary_sequence_executed_parent_runtime_gates_unqualified`, with zero scientific inputs. The status cannot be treated as full qualification: Docker root-layer classification, topology and all parent startup/provisioning/identity gates remain outstanding until the complete registered job connects and verifies them. The runner has not executed against any application.

Six synthetic tests verify full request/actor comparison, observing rather than resending a pending command, terminal-failure handling, parent deadline enforcement, actual stored values for all ordinary producers, and exact warm/restored branch order with first-failure stopping. Sequence tests mock runtime components and do not establish their live compatibility. The original-schema command has passed syntax checking only.
