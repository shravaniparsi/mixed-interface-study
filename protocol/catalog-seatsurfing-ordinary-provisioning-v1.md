# SeatSurfing isolated ordinary fixture provisioning

The CI-only provisioning component is `provision_seatsurfing_ordinary_v1.py`. It requires a published registration binding the exact script hash, selected application revision, current study commit and 30-minute job limit, plus the successful build/inventory report from that same commit. This component does not dispatch a job. The complete ordinary recipe, actor/loader verification, schema compilation, private evidence sealing and coordinator are still required before execution.

Use only a fresh standard public Linux Actions runner. Refuse any pre-existing study application, PostgreSQL, browser, tools-install container or PostgreSQL volume. Do not overwrite or clean another fixture. Create a fresh mode-0700 private directory and retain command output, container inspection, environment files and login configuration there. These files contain synthetic credentials and are private; do not publish raw logs or inspect output. The parent must retain encrypted evidence and tear down its labelled resources even when provisioning fails.

Pull exactly the already recorded PostgreSQL amd64 manifest and Playwright manifest. Verify their recorded configuration IDs and platform. Install the existing frozen browser-tools package lock in the pinned browser image with npm ci, ignore-scripts, no audit/fund and PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1, before application startup. Package installation may access registries; the application network may not. Verify the lock remains byte-identical and Playwright is 1.62.1. The native worker separately verifies Node/Chromium versions and executable identity. Never substitute a different browser version to recover an attempt.

Generate one RSA-2048 PKCS1 private key and PKIX public key with OpenSSL. Persist them for all branches. Key files are 0644 within a host directory of mode 0700, individually mounted read-only so application UID 65532 can read them without exposing the parent directory. Generate synthetic database/admin passwords as 24 random bytes rendered hex and a persistent 32-character CRYPT_KEY as 16 random bytes rendered hex. The original config source requires CRYPT_KEY to be exactly 32 bytes; omitting it terminates startup. Preserve it in the unchanged application's environment throughout all restores, together with its signing-key file paths. The joint checkpoint requires the same application container ID, so recreating a container with new encryption material is not an equivalent restore.

Use the original default organization bootstrap, with name Study organization, user admin, domain localhost, language en and the generated password. Source maps this to admin@seatsurfing.local. Retain the original sample floor/map/spaces, built-in roles, migrations and single-organization settings. Do not edit database records to bypass bootstrap, remove sample data, disable validation or simplify the selected workflow. Read the sole organization ID only after startup for the original password-login configuration. That read establishes neither the authenticated actor nor its permissions; those are later independent checks.

Create PostgreSQL with no external network, no published ports, restart=no, 1 GiB memory and one CPU. Use its original /var/lib/postgresql volume mount (the pinned PostgreSQL 18 image sets PGDATA=/var/lib/postgresql/18/docker). Create the original application image with restart=no, a read-only root, 2 GiB memory/two CPUs and exactly the two signing-key mounts. It joins PostgreSQL's network namespace and listens on 127.0.0.1:8080. The future browser joins that same network namespace. No network bridge, host network or public port is permitted. Container inspection must verify identities, labels, network, mount scope, read-only root and absence of published ports/privileged mode.

The application connects to the local database with the generated password. Set PUBLIC_SCHEME=http, PUBLIC_PORT=8080, STATIC_UI_PATH=/app/ui, CACHE_TYPE=default, DEV=0 and DISABLE_PASSWORD_LOGIN=0. Set MOCK_SENDMAIL=1, empty plugins/feature flags, DISABLE_VERSION_CHECK=1 and DISABLE_ANONYMOUS_USAGE_STATS=1. The original sendmail mock path avoids transport; no message is requested. Network isolation remains mandatory even when these switches are set. Keep all other original configuration defaults.

Provisioning has a shared 300-second deadline for pulls, tools, key generation, startup and evidence. Start PostgreSQL once; observe readiness with at most thirty one-second-spaced pg_isready probes. Start the application once; observe the original container health status for at most ninety one-second-spaced inspections. Readiness observations are not repeated initialization or application-start commands. A stopped/unhealthy process, timeout, identity mismatch, invalid layout or ephemeral-JWT fallback log fails the attempt without automatic restart or remediation. The original healthcheck contract must still be mapped before final qualification registration; this component does not assert its semantics from health status alone.

A successful result is `isolated_fixture_ready_browser_and_actor_unqualified`. It records fixture/key/tool identities and the private native-login configuration. No browser is launched, no study location is created, no user-facing action is taken and no scientific input is executed by this component. Native login, actor verification, complete warm/restored comparisons, original schema and scientific case gates remain separate. The parent must stop and retain a failed fixture; it must not interpret failure as a frontend/API incompatibility.

Validation: Python compilation and eight synthetic tests of environment/layout guards only. No Docker, image pull, dependency installation or application startup occurred during preparation. The tests reject external database networking, published application ports, writable app roots/keys, wrong database images and extra mounts, and verify the required bootstrap key and local settings. These tests do not prove live deployment or restoration.
