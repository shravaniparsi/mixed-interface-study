# Isolated article-creation database diagnostic

The v8 title-151 case returned 500 from both API producers and subsequent list reads, leaving post-failure state unreadable through that API. Its missing-evidence halt remains unchanged. Archived logs identify ArticleOutSchema and ArticleListOutSchema title-length validation failures. At the pinned backend revision, article creation exits its transaction before output serialization. These observations motivate a database test; they do not establish a committed row by themselves.

This fresh API-only diagnostic executes the exact previously exposed article-valid, article-title-150 and article-title-151 payloads, once each, from independently restored copies of the same three-article fixture. Source, payload and policy checks occur before fixture creation. The ordinary case is an implementation control; the title-boundary policies remain unknown. No UI, continuation, mutation of application source, automatic retry or resumption of v8 is permitted.

Each case records an independent read-only SQLite backup before the POST, immediately after its response and before any diagnostic readback, after confirmed backend shutdown, and after restart/readbacks. The fixture adds one backup: thirteen snapshots total when completed. Snapshots never overwrite existing files. Connections use query_only with read_uncommitted disabled. The projection includes the synthetic public user and all article primary keys, slugs, titles, descriptions, bodies and owner IDs; credential fields, tag relations and unrelated state are excluded from reported comparisons. Full backups contain synthetic fixture credentials.

The projector allows article creation, absence of creation, extra rows and removal of old rows; these are measured rather than assumed. It separately reports newly inserted rows matching the requested title/description/body/owner, preservation of fixture rows and user state, selected-state equality, and whether immediate post-response selected state survives shutdown and restart. HTTP status remains a separate observation. No assertion requires the 151-character case to fail or persist.

Readbacks cover the user, author-filtered and global article lists, all fixture detail URLs, and detail URLs for any added slugs found in the immediate snapshot. Added-reference routing is database-derived and explicitly confined to this diagnostic, not a native UI continuation. The same path sequence is used after restart. The verifier reopens all backups, reconstructs projections and derived paths, validates exact event order, all commands, reset hashes, source/selection/bootstrap bindings, and cleanup. No extra writes or omitted/extra snapshot stages are admitted.

The manual workflow has a 480-second outer execution limit and retains all failed attempts. Results support only the pinned SQLite deployment and measured fields. The historical v8 halt and primary freeze gates remain unchanged. A live run follows source review, meaningful database tests and full CI.
