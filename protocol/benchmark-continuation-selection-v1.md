# Benchmark-authored continuation candidates: selection gate v1

## Decision and contribution boundary

Proceed with capability qualification of a fixed candidate cohort, not scientific execution. The purpose is to test generalization of the closed continuation study to benchmark-authored dependent actions in applications not executed in that study. This is a stronger sampling basis than inventing follow-up edits after outcomes. It is not an algorithm novelty claim, untouched-benchmark claim, or assurance of Q1 suitability. The previous null results remain immutable.

The selection followed complete inspection of the 190 distinct template IDs (191 site/template combinations because template 42 spans site groups), then inspection of instances for eight potentially compositional templates. It preceded API-schema inspection, application source inspection for these workflows, evaluator inspection, runtime qualification and outcome observation. Literature examples, normal knowledge of repository lifecycles and earlier benchmark summaries were already exposed. A conjecture that an empty repository may constrain Web IDE actions is prior reasoning, not an observed result or reason to drop other families. All six identified candidate families remain, including likely unsupported ones.

## Fixed frame and candidates

Use the pinned WebArena-Verified task file at commit 6473f72db5dcefc97b5725b59e734504edc28a21. Select explicit creation followed by an action depending on the created entity from the reviewed descriptions. The frame is the archived 812 tasks; the following is an analyst-coded candidate subset, not a mechanical exhaustive semantic classifier or random sample.

1. Reddit post to comment: template 9, all instances.
2. GitLab repository to README creation through Web IDE: templates 87 and 88, all instances. Keep the two content-source strata visible, but treat the continuation mechanism as one family.
3. GitLab issue to assignment/due-date setting: template 327, all instances. Creation and assignment may be expressible in one request; qualification must establish a meaningful separate native action without contradicting the user goal.
4. GitLab merge request to reviewer assignment: template 335, all instances, subject to the same caveat about decomposing a single form.
5. GitLab project to member addition: template 2100 all instances and template 332 instances whose intent explicitly includes adding members. Template 332's creation-only instances remain excluded with their IDs.
6. GitLab directory to file creation: template 84, all instances. A directory may not be a separately persistable resource; absence of a legitimate API producer excludes this family rather than inventing a surrogate creation action.

No substitutions after qualification failures. Within each family pick one capability representative by the minimum SHA256 of 'benchmark-continuation-v1:' plus decimal task_id. All candidates remain in the denominator, including the nonrepresentative instances. Representatives are engineering qualification cases, not the final scientific sample or independent defect counts.

## Qualification before scientific registration

First identify versioned application/API documentation and distributable environment artifacts. Preserve original benchmark task semantics or explicitly itemize every adaptation. External information retrieval needed for README content must not be silently replaced by invented content and still called an original benchmark task. If a reduced continuation-only task is used, label it as adapted and freeze its content independently of outcomes.

Require a documented write-capable API distinct from mere invocation of the native form endpoint, legitimate isolated actors/fixtures, a native dependent action, deterministic reset, and readback of changed and preserved fields. No third-party messages or live hosted-service writes. Reddit API support is unknown; retain failure if absent. Do not provision gated ServiceNow instances or paid infrastructure.

Resource feasibility, authentication, independent reference validity and native/API operation mapping must be resolved before any scientific run. No frontend constraint or generated-tool outcome may be used to construct the API input inventory. Freeze that inventory from versioned source API contracts before native constraint inspection. Existing knowledge and any qualification outcome exposure must be disclosed.

## Mandatory comparisons in a later protocol

A later scientific registration must include native producer plus native continuation, API producer plus native continuation, and API producer plus API continuation, with matched fresh state and actors. An API continuation must receive a complete valid write projection and the same relevant contract information as other branches. Shared frontend constraints must be credited to all baselines. Measure initial producer-state differences before interpreting continuation differences: failure of logical producer equivalence is not evidence of a substitution bug. Handle intentional defaults, permissions and lifecycle restrictions explicitly.

Both ordinary controls and independently enumerated source-valid inputs must be frozen with sample size, repetition, cost and stopping rules before dispatch. Count mechanism families and applications separately from task instances, parameter variants and repeated runs. Confirm effects by raw HTTP/native evidence, persisted readbacks and counterfactuals permitted by that future protocol. No requirement-backed defect is inferred from a channel difference alone.
