# Authored checkpoint and title-repair qualification v1

This is a new development fixture, not a new scientific cohort, retry of the
previous fixture or reopening of a closed application. Publish schedule, code,
workflow, dependency bindings and this protocol before its only dispatch. Use
one standard free ubuntu-24.04 runner, Node 20.20.2, locked Playwright 1.62.1 and
its Chromium. Twelve-minute job cap and 180-second fixture execution cap. No
paid service, external app or local browser execution. Retain any failure.

There are two engineered producer states (ordinary title and null title) and
eight fixed branches. For each state, create a record through JSON, load the
ordinary browser form, establish the actor cookie and a benign localStorage
value, and capture the entire file, API record, browser storage and form values.
The warm branch runs first without restoration. Restored sham and title-repair
branches each restore the same saved file and browser storage, rebuild the HTTP
server at the same origin and navigate a fresh browser context to the form.

The fixture has one JSON file, no background jobs and a request handler that
reads the file on each request. HTTP server replacement happens within the same
Node process; this is not process/container/database checkpoint qualification.
Form state is entirely server-rendered fields; this does not model arbitrary
JavaScript heap, service-worker or asynchronous application state. Cookie and
localStorage equality is checked explicitly, not inferred from record equality.

Before every continuation, require matching full disk bytes, full API record,
server-observed actor, browser storage and form values. The ordinary fixture
also contains two deliberate bad restores: change Description in the restored
file, or remove the actor cookie. These branches must be rejected before any
native POST. Actor failure takes precedence when both actor and state gates fail.
Expected labels are frozen in schedule.json; outcomes are derived from measured
gates, requests and state, not assigned from those expected labels.

All admitted branches fill Description with Edited description and click the
ordinary Save button. The repair branch additionally fills Title with Repaired
title through the normal UI before that same click. This is a prescheduled
control-value intervention, not a hidden database repair, forced Save, injected
validity or programmatic submission. Compare form data before the click: repair
must differ from sham only at Title. Before this intervention, both branches
must have matched the original checkpoint. Preserve all actual submitted bodies.

Require the warm and restored-sham branches to agree on form data, outcome and
full resulting record. For the ordinary state both must continue. For null Title
both must block, produce one observed native invalid event and no POST within
the fixed 500-ms window, and preserve the record. Repair must allow continuation
for both states and commit only Title, Description and the specified version
increment. Full-state comparison must reject extra changes. The intentional
Title change is never described as target preservation.

The missing-title sham/repair contrast checks an engineered causal mechanism;
it is not statistical or natural-application causal evidence. The ordinary
repair control tests that repair does not independently break an already valid
record. The two negative restore controls test gate rejection. Branches are
correlated controls, not independent defects. One fixture run cannot establish
checkpoint portability, generic no-request detection, API-counterfactual request
matching, superiority over source-aware testing or publication contribution.

Only if all eight expected outcomes and complete comparisons hold may this
specific authored procedure be called qualified. No additional states or reruns
are added after seeing results. Any later development version needs its own
published changes and bound; scientific studies remain separately gated.
