# SeatSurfing original rate-limiter qualification condition

Before any runtime outcome, retain the original limiter defaults explicitly in fixture configuration: RATE_LIMIT=250 and RATE_LIMIT_PERIOD=1-M. These equal the already acquired original defaults; the limiter is neither disabled nor relaxed. Sources and its in-memory per-authenticated-user counter are documented in notes/catalog_seatsurfing_transport_followup_v1.md.

For each original application process lifetime (original warm, restored native, restored API), require no more than 200 authenticated requests in TOTAL. This leaves at least fifty requests below the original 250-per-minute limit without estimating minute boundaries, allowing counter resets, delaying a request until a limit clears, or reconstructing the in-memory counter. Any observed 429 makes qualification unavailable. No limit-related rejection can become evidence of frontend validation.

Native counts use each browser worker's final complete trace, including all request endpoints and resource types. Each request requires exactly one header, response and completion observation; duplicate IDs, orphan metadata, pending activity and failed captures are rejected. Anonymous requests remain counted in the total traffic inventory but are excluded from authenticated counts according to the original middleware. Every Authorization value must match the original native bearer token. API counts include original creation in the warm lifetime, and independent startup loading plus continuation loading and all writes in the restored API lifetime. The restored native lifetime has no independent API traffic. This is an aggregate evidence requirement, not permission to issue 200 new requests.

The coordinator runs this check only after complete ordinary comparisons. It resumes and closes the final idle browser, stops the application, verifies actual stopped identity and checks the limiter values in the actual retained container configuration. It reads bounded original final traces and API result artifacts, binds the API results to those already observed, records input hashes, and computes the three budgets. The parent must still establish that all allowed client processes and commands are accounted for and finish broader transport qualification, encrypted retention and cleanup. Rate-budget success alone is not application or study qualification.

Six synthetic tests cover threshold/margin, combined traffic, anonymous/create-envelope accounting, throttling, incomplete/orphan observations, defaults and actor identity. The coordinator test covers all three lifetime inventories and refusal when warm native plus producer traffic exceeds the bound. No application is executed by these tests and the study remains at zero SeatSurfing runtime attempts.
