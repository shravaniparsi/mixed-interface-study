# SeatSurfing observed write-header rules v1

These prospective rules apply only to original location POST creation, PUT update and location-attribute POST writes at the fixed application revision. They are not a general claim that HTTP headers do not matter. Source evidence is already frozen in wave2/52 (routes, body parsing, middleware and request-user lookup), wave3/39 (location routes), wave33/6 (configuration), wave33/7 (native login/session creation), and wave34/2 (middleware installation).

The original UnmarshalBody reads r.Body and performs json.Unmarshal; UnmarshalValidateBody then invokes the original validator. Location create/update use the parsed model, route ID, authenticated user and repository/service objects. The attribute setter similarly uses route IDs, original user permissions and parsed value. GetRequestUser reads the context user ID installed by the original Bearer middleware. The installed middleware sequence is security/CORS, authentication and the original per-user rate limiter. These location write paths do not inspect User-Agent, Accept-Language, Accept-Encoding, client hints, Fetch Metadata or Priority. User-Agent use during native login is retained in the original shared session; the API branch does not replace that login.

Observed Authorization and JSON Content-Type must agree, Host must be the exact isolated origin, and both complete JSON bodies must agree. Observed Content-Length must equal its own body's UTF-8 byte length. Chunked framing, request compression, cookies, forwarding headers, method overrides and every unlisted header are rejected. Accept may only be absent or */*; Connection absent or keep-alive. Origin may only be absent or the exact same origin. Fetch Metadata, if present, must describe an empty same-origin resource with cors/same-origin mode. Metadata values remain retained; the rules do not delete differences from evidence.

The original CORS allowlist is empty outside development mode. Provisioning now explicitly retains CORS_ORIGINS='' alongside PUBLIC_SCHEME=http and the original limiter defaults, preserving that behavior. SetCorsHeaders only emits access-control response headers for a configured allowed origin; no alternate allowlist is admitted by this rule. Browser requests remain same-origin, and HTTP responses/persistence are independently checked. This is not a qualification of cross-origin behavior, preflights, TLS, proxy routing or custom plugins.

The bounded metadata difference set is: accept-language, accept-encoding, user-agent, sec-ch-ua, sec-ch-ua-mobile, sec-ch-ua-platform, sec-fetch-dest, sec-fetch-mode, sec-fetch-site and priority. Each retained difference is labelled with its specific source-based disposition. Structural differences retain separate descriptions. These are checks of OBSERVED headers only. The known diagnostic Content-Length gap is not filled in, and the result explicitly keeps API header capture and request-body wire capture incomplete. Before an enclosing runtime can qualify transport, it must calibrate the passive capture against an actual synthetic receiver in the pinned Node 24.18.1 runtime, bind the actual fixture configuration, account for all client traffic and apply the observed rules to actual matched writes. Loading/readback equivalence remains independently required.

Five synthetic tests cover retained metadata differences, unknown and interpretation-changing headers, changed actor/host/origin, incorrect body framing/JSON, route scope and altered CORS configuration. The original provisioning tests check the unchanged explicit defaults. No application or scientific case is executed. This rule component is not yet the enclosing runtime qualification gate.

## Pinned-runtime receiver calibration integrated into provisioning

Before dependency-tool installation or application startup, provisioning invokes the synthetic receiver calibration once inside the already verified pinned browser/Node image. That container has network=none, a read-only root, the runner UID/GID, 256 MiB/one CPU and only the study source mounted read-only. Its temporary server listens on its own loopback address and sends exactly three synthetic requests: GET, POST and PUT, including a UTF-8 body. It contacts no application, external host, database or browser page. A twenty-second worker deadline and thirty-second parent command deadline apply; no calibration retry is authorized.

The receiver records the headers and body actually received. Every diagnostic header must match the receiver's value; the only admitted receiver-only header is Content-Length, whose received value must equal the actual body byte count when a body exists. The report retains the complete synthetic receiver observations, diagnostic observations, exact missing-field lists, Node and Undici versions. Provisioning requires Node 24.18.1 and records the calibration output path/hash. A failure prevents application startup rather than silently waiving instrumentation support. A timed-out calibration container remains the parent's cleanup responsibility; the named resource is checked absent before provisioning.

Local synthetic GET/POST/PUT calibration passes under the existing Node 22.22.3 tool runtime. This verifies the calibration harness, not pinned-runtime behavior; Node 24.18.1 has not yet been run. The actual registered qualification must produce its own pinned calibration evidence before the observed write-header rules can be applied to application traffic. No SeatSurfing runtime attempt was dispatched during this preparation.

## Connected offline transport gate

The stopped ordinary coordinator now binds the provisioning calibration path/hash to the original artifact and captures the actual stopped application's CORS, scheme and limiter configuration. It assembles a private bounded bundle containing the complete request comparisons, native/API producer evidence, independent API continuation evidence and all three request budgets. The offline verifier rechecks the calibration's Node 24.18.1 identity, synthetic methods/bodies, actual receiver headers and admitted diagnostic gaps, then reconstructs the producer and continuation diagnostic mappings rather than trusting saved parsed headers.

Both native continuation branches and the native/API ordinary producer must satisfy the observed write-header rules. All three original-rate-budget results must pass. The verifier emits a new private result tied to the exact input-bundle hash; changed calibration bytes, altered diagnostics, unlisted receiver-only headers, incorrect runtime identity, unknown native headers or an exceeded budget prevent success. The parent records the stopped container identity and requires that exact result binding. No new HTTP request is made by this gate.

The resulting phase is `ordinary_write_transport_verified_parent_gates_pending`, not application qualification. It preserves incomplete packet/header-capture facts, source scope and the requirement for all-client inventory. The enclosing runner still owes original-schema execution, complete client/resource accounting, deadline enforcement, encrypted evidence retention and immutable registration; both ordinary edit cycles must pass. Five synthetic Node gate tests include a real offline file invocation, and the twentieth coordinator test exercises success plus calibration/result-hash rejection. Test fixtures explicitly use synthetic reported runtime metadata; they are not evidence that the pinned runtime has executed.
