# Two ordinary-valid producer-route controls

Freeze one UI-create/UI-edit arm and one API-create/UI-edit arm, each in a separate fresh GitHub job/application database and browser context. Reuse the fixed application JAR, Elasticsearch digest, Java, Node, Playwright and Chromium versions from native-login-v1. Public isolated fixture credentials admin/admin come from the pinned administration Cypress test. No hosted service, paid call or invalid payload is used. Each job is capped at 25 minutes, browser execution at 180 seconds. Run each arm once, retaining failures and not-run stages.

Both arms use this exact create body: id=null, login=studycontrol, firstName=Study, lastName=Control, email=studycontrol@example.com, activated=true, langKey=en, authorities=[ROLE_USER]. UI creation must emit this body through the original form; a difference is recorded as an equivalence failure, not repaired. API creation sends those JSON values with the token obtained by the native admin login. Do not inject a login token or change the application. The API client is explicitly part of the API arm and readback observer, not claimed as UI behavior.

Require successful admin UI login and account readback with ADMIN authority. Both arms must receive create status 201, then GET /api/admin/users/studycontrol must expose a non-null ID and matching business fields. Navigate to the original /admin/user-management/studycontrol/edit page, check loaded field values, change only firstName to Edited, and submit through the native form once. Require PUT status 200 and independent API GET readback with the same ID, changed firstName, and all other controlled fields unchanged. Record producer request body, projected readbacks, native control values, save-enabled state, response status/path and screenshots. API-observed readback demonstrates persistence through the application read endpoint, not direct database auditing.

The UI arm enters /admin/user-management/new, fills the established field-name selectors, selects ROLE_USER/en, checks the activated state, and submits once. No guessed fallback routes/selectors, retries, corrective payloads or additional mutations. Browser routing allows only same-origin reads, one authentication POST, one create POST, and one update PUT per arm. API observer methods/paths are fixed. No delete or external traffic; discard the isolated databases at cleanup. Auth tokens remain in memory only and are not archived.

This is development harness qualification on an exposed application, not a natural-defect study or a sample-size increase. Successful controls establish ordinary workflow operability and matched controlled inputs, not prevalence, causation of a failure, agent performance or Q1 novelty. The candidate-algorithm claim remains retired. No defect search or reserved-source access follows automatically from this control.
