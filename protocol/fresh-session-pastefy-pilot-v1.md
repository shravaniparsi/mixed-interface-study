## Question and scope

Can a successful API-created record support an unrelated ordinary edit in the original native UI, and does a fixed target-field repair change that outcome relative to a sham? This is a development pilot on one exposed application/workflow, not an independent application evaluation, a representative prevalence estimate, or independent natural-input benchmark. ## Fixed inputs and ordering

The executable generator and manifest bind six cases: ordinary-content, ordinary-title, content-omit, content-null, title-omit, title-null. Content precedes title by deterministic field order. Ordinary inputs contain title `study-note`, content `Disposable ordinary study text.`, PASTE mode, UNLISTED visibility, encryption false, empty tags and ai true. The original server has AI disabled; ai true matches the native serializer. Filename extensions are absent because the original client automatically adds language tags for them. Folder, expiration and fork references remain omitted.

Each altered payload changes exactly one field. Each case edits the other field: title becomes `study-note-edited`, or content becomes `Disposable revised study text.`. Repair is an original API PUT containing only the target field's ordinary value. Sham is the same endpoint and method with an empty object. Both are potentially version-changing writes; the analysis must account for the actual original save semantics rather than assume sham leaves metadata unchanged. Do not adapt repairs to errors. Ordinary controls must qualify both field pairs, both intervention branches, the client probe and scoring before any altered case runs.

## Per-case execution and evidence

1. Restore the same verified empty application checkpoint, authenticate the fixed actor and issue the exact original API POST. Save the request, status, response body and full persistent-state observations even on rejection. HTTP errors are outcomes; connection failures are unavailable execution. A successful producer needs response success, one newly persisted owner-bound paste, exact readback agreement, and an explicit accounting of normalization and all other state changes. A success response with absent or different persistence is a separate outcome, not an editable record.
2. For each accepted/readable record, checkpoint the produced state. Restore it for an original-client prediction probe, for sham, and for repair. Record restored-state equality before each branch. Rejected or unreadable producer outcomes remain in the denominator and receive explicit not-applicable continuation fields.
3. The client probe loads the record and performs the fixed unrelated edit through original controls in a fresh context. Capture the original serialized write at a pre-forward interception boundary, then abort it: no prediction-probe write reaches the server. Verify the database and files equal the starting state afterward. Record native validation feedback, disabled controls and JavaScript errors as distinct evidence. A timeout or exception alone yields unknown, not a prediction of validation blocking.
4. Sham and repair each restore the identical producer checkpoint, issue their fixed original API PUT, stop the application and verify the exact intervention delta. Relaunch and perform the same unrelated native edit from a fresh context. Record full request/response, readback and post-state. The repair branch must demonstrably persist the target ordinary value before continuation. All branches run even when sham already succeeds; no selection based on observed failure.
5. Cleanly stop all writers, recover sanitized evidence through the qualified checksum transport and run an independent outcome classifier on private observations before export. Branch failures must not erase earlier records or suppress later scheduled cases. Infrastructure repairs require a prospectively recorded code amendment; previous outcomes remain visible and any changed logic is not silently pooled.

## Comparators and classification

H reports original producer acceptance plus exact persisted readback; it does not predict native editability by definition. S uses the original `docs/openapi.json` OpenAPI 3.0.3 creation request schema, internal references resolved offline, with the pinned OAS30Validator package. The frozen schema predictions concern creation-request conformance only. The original schema and its MIT notice are retained unchanged. Runtime annotations and original schema disagreements are described, not replaced with a researcher-authored schema.

D reports whether the original loaded client produces the intended native request before transmission, including its original defaults, conditional fields and serialization. Its probe precedes sham/repair outcomes and is run from an identical restored state. Emitted request, positive client blocking, client crash and unavailable probe remain separate. D is not credited with predicting successful server persistence. Report each comparator's target and coverage; do not calculate one accuracy number over unlike targets.

The continuation classifier distinguishes exact intended edit, unintended persisted changes, positive client validation blocking, server rejection, client runtime failure and unavailable execution. A successful HTTP response alone cannot establish exact editing. The state frame covers all original application tables, schema, sequences and application files, with original version/timestamp/content-hash changes accounted for. A native title inference or normalization that changes an unrelated field is reported explicitly rather than automatically treated as a defect.

A repair effect requires equal producer states, valid sham and repair execution, verified repair persistence, identical continuation actions and a changed continuation outcome. For these generated variants, report exact paired counts by field and mechanism. Four altered variants do not become four independent application defects. Product-defect attribution additionally needs a pre-existing compatibility obligation; absent such an obligation, use observed interface incompatibility or unresolved attribution. No agent-improvement or Q1-readiness claim follows from this pilot alone.
