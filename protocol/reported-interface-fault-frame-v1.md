# Bounded reported-fault frame feasibility screen

Freeze this protocol and collector before retrieval. This is a research-design feasibility screen, not a new scientific execution cohort. It responds to a contribution gap: ordinary successful benchmark tasks do not by themselves supply sensitivity evidence for validation-gap detection. Do not reopen any closed application schedule or count reported faults as newly discovered defects.

Use exactly one GitHub public issue-search request, query `is:issue is:closed label:bug "api" "validation" "frontend" created:<=2025-12-31`, sorted created ascending, page 1, per_page 50. The cutoff, terms, order and 50-result bound are fixed before seeing the results. Do not change terms, add pages, replace irrelevant results, search for a passing reproduction or contact issue participants under this registration. Empty or irrelevant results are retained as the outcome of this frame screen.

This is the first 50 results of one search-return frame, not all GitHub bugs or a random population sample. Search indexing, English terminology, the bug label, closed status and chronological ordering introduce selection bias. Total_count and incomplete_results describe the search response, not verified defect counts. Closed status and a bug label do not prove a bug was fixed or even valid. Query exposure already selects suspected failures; no prevalence or general discovery-rate claim is possible.

Store the exact raw API response outside the public repository with its SHA-256. Publish only issue identifiers, repository/URL, dates, labels, bounded title metadata, and hashes of full title/body plus the query/retrieval context. Do not publish full issue bodies or author profiles. No task-generated or model-generated input is introduced. Do not inspect linked patches or run code during collection.

After collection, review every returned row with the same eligibility questions: does the report identify an API-produced state and a browser-native operation; is the divergence a validation/business-state problem rather than pure authentication, rendering, schema tooling or content generation; are a failing version and a reproducing input recoverable; is there independent maintainer/fix evidence; can the exact subject be run within the budget; does it overlap previously exposed project cases? Unknown answers remain unknown. No result is a confirmed defect until its causal reproduction and fixed-version contrast are independently checked under a later protocol.

The scientific role, if feasible, is retrospective sensitivity comparison under information-matched inputs. Give the API comparator the same task expectations and required predicates; do not use issue text or patches as privileged information for only the proposed method. Cases sharing a root cause, project or fix remain clustered. A historical fault benchmark could measure sensitivity, not establish natural-defect discovery, selector superiority, agent benefit or Q1 readiness by itself. Method novelty and representative negative cases remain separate gates.

Stopping rule: one metadata collection and complete retained-row review only. No application runs, dependency installs, paid model calls, large artifact downloads or additional queries follow automatically. Before admitting any execution set, assess relevance, version/input recoverability, independence, prior exposure, baseline fairness and a concrete contribution claim. The existing fifteen-task benchmark frame is retained unchanged; this screen does not replace its inconvenient or failed cases.
