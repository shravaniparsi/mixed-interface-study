# Runtime configuration oracle calibration: NetBox defaults

This exploratory historical calibration tests issue 18669, exposed through the frozen Defects4REST census. It is not an independent discovery, blind evaluation, or a new-method claim. Parent cac41cd093b7fdcf96e9525bd7c01b5dad4aaedb and direct fixing child c108c738aeac419bfeabcd1e49899872c69a0831 are compared without application edits. The fix adds population of omitted defaults at save time. The existing closed cohorts remain unchanged.

Question: can configuration retrieved through the API provide expected custom-field values for creation, including controls that must preserve explicit null, false, zero and nondefault values? This isolates one candidate source of semantic expectations. Generic configuration and metamorphic testing have prior art; novelty of any extension remains unestablished.

Use the real Django REST routes through APIClient, real PostgreSQL and Redis, with an authenticated disposable superuser. This bypasses the HTTP transport and authentication handshake and cannot establish their correctness. It executes application serializers, views, persistence and readback. Fresh services per version; no mock storage or extracted replacement implementation.

Create optional custom fields for ipam.prefix through the API: text default alpha, boolean default true, integer default 7, and a text sibling without a default. Read their metadata back. Six creation cases: omitted map, empty map, sibling only, explicit overrides, explicit text null/boolean false/integer zero, and a partial override. Repeat the same six cases after changing defaults through the API to beta/false/0 and reading metadata back. Use separate prefixes for every creation. Expected values come from the retrieved configuration and explicit input; missing entries inherit declared non-null defaults, while present entries retain their supplied values. This rule is manually specified from the documented historical requirement, not automatically inferred.

Record complete request bodies, status/body, persisted readback, and database custom_field_data. A status-only baseline checks 201 creation and 200 readback. Configuration checking compares all three configured fields at response, API readback and database observation. Sibling contents are also checked when supplied. Separately count missing versus mismatched keys. Setup failures do not count as semantic detections. Require all four configuration creations, configuration updates and metadata retrievals to succeed. No ranking or significance claims from correlated cases in one historical fault.

Two sequential Ubuntu jobs with a 15-minute cap each, zero model calls. Each job installs the unchanged pinned project's requirements and records resolved packages, source commit, study commit and instrument hashes. Preserve migration/install failures and partially completed results. No automatic retry. At most one separately documented infrastructure correction may be considered if the first attempt cannot reach the application. Do not repair the application or discard disagreeing controls.

Success for feasibility requires complete execution on both pins and an interpretable comparison, not a particular number of detected cases. A broader contribution would need independent projects, a defensible configuration-to-oracle mapping, appropriate existing-tool baselines and tests on previously unexamined cases.
