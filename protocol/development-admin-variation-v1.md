# Fixed development input-variation experiment

This is harness and mechanism development on the already exposed 21-points application, not independent evaluation. The ordinary paired controls qualified in run 44105779135. All four editable text controls in the qualified user form (login, firstName, lastName, email) enter this schedule, without selecting by expected failure. Apply omission and explicit JSON null separately to each field of the exact ordinary create body. Include one unchanged control: nine cases total, one fresh job/database/browser per case. All cases and code are published before any outcome is observed.

Reuse the fixed application binary, original UI, isolated namespace, admin actor, dependencies and hostname correction of admin-control-v2. Each case gets one authenticated API POST. A 4xx is producer rejection, not evidence of accepted incompatible state. Other non-201 statuses are unexpected producer responses. An accepted payload with no usable login is unaddressable by this fixed observer, not automatically incompatible. For 201 with the fixed login, read back the persisted record and then load its original native editor; check all four text values against readback (null/absent renders empty). Record save availability on load and after editing an unrelated field: firstName becomes Edited, except firstName-target cases use lastName.

If save is disabled after that edit, restore only the varied field to its ordinary value using the native control. Record whether save becomes enabled. Submit at most one native PUT when enabled, retaining its body/status and final API readback. A successful update requires the same object ID and intended unrelated edit; a repaired case also requires the restored target value. This is a paired repair observation, not population-level causal inference. No alternate repair, payload escalation, retries or post-outcome case additions are allowed. Retain all observed normalizations and non-target changes for analysis; do not infer that unchanged non-target fields were verified merely from HTTP success.

Outcomes: producer_rejected; producer_unexpected_status; accepted_unaddressable; native_edit_saved; blocked_then_target_repair_saved; repair_submit_rejected; native_submit_rejected; native_save_disabled_after_repair; or harness failure/not-run. A disabled save plus a persisted record supports editor incompatibility for that state, not automatically a violation of a documented API obligation. Original source shows native email is required, which is prior exposure, not a discovered independent requirement. Omission and null variants from one field/workflow must never be counted as independent defects.

Bounds: nine jobs, max three concurrent, 25 minutes/job, 180 seconds/browser, existing fixed build artifact, no paid model calls, no hosted-app traffic, free standard public Actions. Native browser routing permits local reads, one authentication POST and at most one update; API producer and readback paths are fixed. Tokens are not saved. Archive response bodies only from synthetic isolated data. Archive failures, response logs, screenshots and exact artifact identities. Close this schedule after this execution regardless of findings. A green job means measurement completed, not that the input was valid or compatible. Zero independent cases are added.
